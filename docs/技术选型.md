# 元矩阵 MetaMatrix · 技术选型

> 配套文档：[readme.md](../README.md)。本文给出可执行的栈决策、数据模型与开源对标；二选一处均给出**默认推荐 + 理由 + 备选一行**。

---

## 1. 选型原则

1. **元数据优先**：一切可配置进 JSON；渲染器保持薄。
2. **DOM 优先于 Canvas**：首期以文本/卡片/表单交互为主，调试与无障碍友好。
3. **一处扩展、处处复用**：版本、模板、权限挂在 Document 层，不按画布类型分叉存储。
4. **能借则借、不硬绑**：开源项目作结构/交互参考，默认不直接 fork 整仓作为产品底座。
5. **MVP 可替换**：UI 库、ORM、Patch 库允许在备选条件触发时切换，Schema 契约保持稳定。

## 2. 前端栈

### 2.1 默认推荐

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 框架 | **Vue 3 + TypeScript** | 响应式适合「改 Schema → 即时重绘」；与团队常见 Vue 栈一致 |
| 构建 | **Vite** | 启动快、TS/ESM 友好 |
| 状态 | **Pinia** | 文档级 store 清晰；便于拆 `document` / `ui` / `history` |
| 布局渲染 | **CSS Grid / Flex + SVG 坐标轴** | 对齐结构化四象限；轴与箭头用 SVG 最干净 |
| 拖拽（象限卡片） | **VueDraggable Plus**（SortableJS） | 列表排序、跨象限移动成熟 |
| 拖拽（Markers） | **自研 pointer 拖拽**（或 `@vueuse/core` useDraggable） | 绝对定位 + 百分比坐标，比列表 DnD 更贴合 |
| UI | **Element Plus** | 后台表单、抽屉、表格、消息反馈齐备，MVP 最快 |

**备选（UI）**：Radix Vue / Reka UI 等无头组件——当需要高度定制视觉、且有设计体系投入时再切换。

**备选（框架）**：React + Zustand + dnd-kit——若团队主栈改为 React，或强依赖 tldraw 生态时再评估。

### 2.2 为何首期不用纯 Canvas / WebGL

| 维度 | DOM + SVG | 纯 Canvas / WebGL |
| --- | --- | --- |
| 文本编辑 / 表单 | 原生，易做 | 需自研 caret 或叠加 DOM |
| 无障碍 / SEO / 测试 | 易 | 难 |
| 象限卡片、Tag | CSS 即可 | 重绘成本高 |
| 海量自由图形、复杂笔触 | 一般 | 更合适 |
| 本项目首期形态 | **匹配** | 过重 |

结论：首期坚持 **受约束的 DOM 白板**。若未来单画布 markers > ~500 且需手绘笔迹，再评估 Canvas 图层或嵌入 tldraw shape 层（见 §8）。

### 2.3 组件拆分（建议）

```
CanvasViewport
├── BackgroundLayer          # L1 斜纹 / 底色
├── QuadrantGrid             # L2 CSS Grid
│   └── QuadrantCell         # 标题、Tag、items、watermark
├── AxesLayer                # L3 SVG
└── MarkersLayer             # L4 absolute
    └── MarkerNode
ConfigPanel / VersionDrawer / TemplatePicker
```

## 3. 交互与状态

### 3.1 Pinia 边界

| Store | 职责 |
| --- | --- |
| `useDocumentStore` | `current_data`、脏标记、`head_revision_id`、保存/加载 |
| `useSelectionStore` | 当前选中象限 / marker / 卡片 |
| `useHistoryStore` | 前端撤销重做（内存栈，与服务端 revision 分离） |
| `useUiStore` | 面板开关、缩放比、吸附开关 |

原则：**服务端 revision ≠ 前端 undo**。Undo 是会话级；Revision 是产品级存档。

### 3.2 拖拽策略

1. **象限内卡片**：VueDraggable Plus；`group` 名按画布实例隔离；结束时写回 `quadrants[i].items`。
2. **Markers**：`pointerdown/move/up`；移动中用像素，`pointerup` 换算为 `%` 写入 JSON；可选轴/边缘吸附（阈值 4–8px）。
3. **Axes 层**：`pointer-events: none`，避免挡住 markers。

### 3.3 缩放与导出

- MVP：CSS `transform: scale` 轻度缩放即可。
- 导出：`html-to-image` / `modern-screenshot` 对 Viewport 根节点出 PNG。
- **备选**：画布极大时再引入 pan-zoom 库（如 `wheel-gestures` + 自研容器）。

## 4. 后端与存储

### 4.1 默认推荐

| 层 | 选型 | 理由 |
| --- | --- | --- |
| API | **CloudWeGo Hertz** | 高性能 Go HTTP；Documents / Revisions / Auth 边界清晰 |
| DB | **PostgreSQL** | **JSONB** 存画布树；索引、事务、并发成熟 |
| ORM | **GORM** | AutoMigrate + JSONB；与 Go 生态契合 |
| Patch | **fast-json-patch**（主，后续） | RFC6902；MVP 仅 snapshot 存版 |
| 鉴权 | **JWT**（bcrypt 密码） | 多用户；文档按 `owner_user_id` 隔离 |

**历史备选**：NestJS + Prisma（已归档于 `pros/api-nestjs-archive`）。  
**备选（ORM）**：TypeORM——若团队已有 TypeORM 规范或需更细的 QueryBuilder 控制。  
**备选（Patch）**：`jiff`——需要 patch 逆运算 / rebase 能力时优先评估。

### 4.2 表结构（SQL 草案）

```sql
-- 用户（多用户）
CREATE TABLE users (
  id                  UUID PRIMARY KEY,
  email               VARCHAR(255) NOT NULL UNIQUE,
  display_name        VARCHAR(128),
  password_hash       VARCHAR(255) NOT NULL,
  created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- 当前可编辑文档（不按画布类型分表；JSONB 存全部模板）
CREATE TABLE canvas_documents (
  id                  UUID PRIMARY KEY,
  owner_user_id       UUID         NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  canvas_type         VARCHAR(64)  NOT NULL,  -- 文档 JSON type 或模板族
  title               VARCHAR(255) NOT NULL,
  schema_version      INTEGER      NOT NULL DEFAULT 1,
  current_data        JSONB        NOT NULL,
  head_revision_id    UUID,
  template_id         VARCHAR(64),           -- 如 y-model / star-quadrant
  created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE INDEX idx_docs_owner_updated ON canvas_documents (owner_user_id, updated_at DESC);
CREATE INDEX idx_docs_owner_type ON canvas_documents (owner_user_id, canvas_type);
CREATE INDEX idx_docs_owner_template ON canvas_documents (owner_user_id, template_id);

-- 不可变版本链
CREATE TABLE canvas_revisions (
  id                  UUID PRIMARY KEY,
  document_id         UUID         NOT NULL REFERENCES canvas_documents(id),
  parent_id           UUID         REFERENCES canvas_revisions(id),
  revision_type       VARCHAR(16)  NOT NULL CHECK (revision_type IN ('snapshot', 'patch')),
  payload             JSONB        NOT NULL,  -- 全量 JSON 或 RFC6902 数组
  base_snapshot_id    UUID         REFERENCES canvas_revisions(id),
  author_user_id      UUID REFERENCES users(id),
  label               VARCHAR(255),
  content_hash        VARCHAR(64),            -- 可选：完整性校验
  created_at          TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE INDEX idx_revisions_document ON canvas_revisions (document_id, created_at DESC);

-- 可选：模板表（也可先用静态 JSON 文件）
CREATE TABLE canvas_templates (
  id              VARCHAR(64) PRIMARY KEY,
  canvas_type     VARCHAR(64) NOT NULL,
  title           VARCHAR(255) NOT NULL,
  schema_version  INTEGER NOT NULL,
  data            JSONB NOT NULL,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

`head_revision_id` 可在应用层维护外键一致性（创建 revision 与更新 document 同一事务）。

### 4.3 API 草图

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/documents` | 列表 |
| POST | `/documents` | 从模板或空 Schema 创建 |
| GET | `/documents/:id` | 取当前态 |
| PUT | `/documents/:id` | 保存当前态 + 可选自动 checkpoint |
| POST | `/documents/:id/revisions` | 手动存版；body 含 `expected_head_revision_id` |
| GET | `/documents/:id/revisions` | 历史列表 |
| GET | `/documents/:id/revisions/:rid/materialize` | 物化某版本（只读预览） |
| POST | `/documents/:id/restore` | 原子恢复为新 head |
| POST | `/documents/:id/fork` | 从某 revision 分支 |

## 5. 版本管理详细设计

### 5.1 双层模型

```
canvas_documents.current_data  ←—— 日常读改（低延迟）
         │
         │  存版 / 检查点
         ▼
canvas_revisions (append-only)
  ├─ snapshot : 完整 JSON（锚点）
  └─ patch    : RFC6902 相对 base_snapshot 的增量
```

- **Snapshot**：初始化、用户打标签里程碑、patch 链过长（如 >50）或 `schema_version` 升级时强制生成。
- **Patch**：日常自动保存；只记字段级变更，例如：

```json
[
  { "op": "replace", "path": "/markers/0/x", "value": "18%" },
  { "op": "replace", "path": "/quadrants/0/title", "value": "探索场景 v2" }
]
```

### 5.2 生命周期

| 动作 | 行为 |
| --- | --- |
| 手动存版 | 对 `current_data` 生成 snapshot 或相对 head 的 patch → 追加 revision → 更新 `head_revision_id` |
| 自动检查点 | 定时或「切换类型 / 批量导入」时 snapshot |
| Schema 迁移 | 写入迁移后 snapshot，旧链仍可物化（配合迁移函数） |
| 只读预览 | 找到最近 snapshot，顺序 apply patch → **不写** `current_data`，不影响前端 undo 栈 |
| 原子恢复 | 物化目标版本 → **新写入一条 snapshot 作为新 head** → 再更新 `current_data` |
| 分支 | 设 `parent_id` 指向 fork 点；新 document 或同 document 多 head 策略二选一（MVP 建议 **fork 成新 document**，更简单） |

### 5.3 乐观并发

```
Client                          Server
  |  expected_head = H0            |
  |  PUT/POST save  -------------> |  BEGIN
  |                                |  IF head != H0 THEN 409 Conflict
  |                                |  ELSE insert revision; update head; COMMIT
  |  <------------ 200 / 409 ------|
```

409 时返回最新 `current_data` + `head_revision_id`，客户端提示合并或覆盖（MVP 可仅提示刷新）。

### 5.4 与画布类型无关

`canvas_type` + `schema_version` 决定如何**解释** JSON；`canvas_revisions` 的存取流程对所有类型相同。新增 SWOT 等类型时，版本能力自动具备。

### 6.2 图层与 Z-index（实现约定）

| Layer | Z-index | pointer-events | 备注 |
| --- | --- | --- | --- |
| Background | 0 | none | 斜纹可用纯 CSS，无需图片资源 |
| Quadrant Grid | 10 | auto | Cell 内编辑标题/Tag/items |
| Axes | 20 | none | 避免挡 markers |
| Markers | 30 | auto | 拖拽中临时 40 |
| Selection chrome | 50 | none | 选中框、对齐辅助线 |

### 6.3 扩展预留

- `type: "grid_nm"` + `rows` / `cols`：通用网格（九宫格等）。
- `type: "swot"`：可映射为四象限特化标签，或独立 cell 语义。
- Marker `type` 枚举可扩：`dot | icon | note | image`。
- 坐标统一用 **字符串百分比** 或 **0–1 小数**（二选一写进 Schema；推荐百分比字符串，与 CSS 一致）。

| 项目 | 借鉴点 | 不直接当底座的原因 |
| --- | --- | --- |

| Tabula | 无限画布 TS 框架 | 交互模型偏重，超出「受约束白板」 |
| Excalidraw | `elements[]` 描述、本地历史思路 | 无限手绘白板，约束四象限需大量裁剪 |

| TapCanvas | `flows` + `flow_versions` 双表 | 流程画布领域；模式可借，代码不必整迁 |

| @revisium/engine | 类 Git 修订、Schema 校验 | 偏表格/结构化数据；可作复杂版本期参考 |

## 8. 备选方案与切换条件

| 当前默认 | 备选 | 切换条件 |
| --- | --- | --- |
| Vue 3 | React + Zustand | 团队主栈变更，或强绑 tldraw |
| Element Plus | 无头组件（Radix Vue 等） | 设计系统成型、要强视觉定制 |
| CSS/SVG DOM | Canvas 层 / tldraw shapes | markers 规模与笔迹需求明显上升 |
| Prisma | TypeORM | 需复杂动态查询或已有 TypeORM 基建 |
| fast-json-patch | jiff | 需要 inverse / rebase 工作流 |
| 单文档 fork 分支 | 同文档多 head | 产品明确要求 Git 式多分支同页 |
| 仅 snapshot | snapshot + 长 patch 链 | 存版频繁且存储成本成为问题（M3） |

## 9. 首期落地建议（MVP 边界）

### 9.1 做

1. 定稿 `schemaVersion: 1` 与 STAR 模板 JSON（可先放 `pros/web/src/templates/`）。
2. 前端：Viewport 四层渲染 + ConfigPanel 改轴/象限/watermark + Markers 拖拽。
3. 后端：Hertz + GORM + PG；多用户 JWT；Document CRUD；**仅 snapshot 存版** + 预览/恢复 + 乐观并发。
4. 导出 PNG；基础空状态与错误提示（Element Plus）。

### 9.2 不做（写入迭代 backlog）

- Patch 链压缩、字段级 Diff UI、同文档多分支。
- 实时协同、权限、评论。
- SWOT / 九宫格模板（M4 再用同一引擎验证）。
- 深色主题、移动端完整适配、WebGL。

### 9.3 风险与取舍

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Schema 过早过度设计 | 延误 MVP | 只锁定 quadrant + markers；其余类型后置 |
| 绝对定位 markers 与轴遮挡 | 交互差 | Axes `pointer-events: none` + 吸附 |
| 只存 snapshot 存储膨胀 | 成本 | M3 引入 patch；里程碑强制 snapshot |
| 乐观并发冲突体验差 | 用户困惑 | MVP 明确 409 提示；暂不做自动三路合并 |
| 误用自由白板库 | 工期失控 | 坚持 DOM 约束白板；开源仅对标不整仓引入 |
| 中英文文案与 STAR 语义漂移 | 模板不一致 | 模板 JSON 单一事实来源；文档与代码同仓 |

### 9.4 建议开工顺序

```
Schema + STAR JSON
  → 静态四层渲染
  → 编辑与 markers 拖拽
  → Pinia 持久化到 API
  → snapshot 版本
  → 导出与打磨
```
