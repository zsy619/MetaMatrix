#### 三、 通用画布架构设计

为了后期扩充到其他画布（如 SWOT、艾森豪威尔矩阵、商业模式画布），建议采用以下结构：

##### 1. 核心数据结构（JSON Schema 示例）

任何画布都由一份 JSON 配置决定，前端组件只负责解析和渲染：

```json
{
  "id": "canvas_001",
  "type": "quadrant", // 画布类型，未来可以是 "grid_9" (九宫格), "freestyle"
  "theme": { "primaryColor": "#333" },
  "axes": {
    "x": { "leftLabel": "个人", "rightLabel": "组织" },
    "y": { "topLabel": "上限", "bottomLabel": "下限" }
  },
  "quadrants": [
    {
      "position": "top-left",
      "title": "探索场景",
      "tag": { "text": "兴奋突破", "bgColor": "#fce8e6", "color": "#d93025" },
      "items": [] // 可以存放具体的卡片或列表
    },
    {
      "position": "top-right",
      "title": "变革场景",
      "tag": { "text": "终局预判", "bgColor": "#e8f0fe", "color": "#1a73e8" },
      "items": []
    }
    // ... 其他象限
  ]
}
```

##### 2. 组件拆分设计

- **`CanvasContainer`**：最外层容器，处理缩放、平移、背景网格、主题注入。
- **`CanvasAxes`**：接收`axes` 配置，使用 SVG 或绝对定位的 Div 渲染坐标轴、箭头、文字标签。
- **`QuadrantGrid`**：将画布切分为 4 个区域（CSS Grid:`grid-template-columns: 1fr 1fr; grid-template-rows: 1fr 1fr;`）。
- **`QuadrantItem`**：单个象限组件。内部包含标题、自定义标签（Tag）、以及可扩展的内容插槽（Slot）。
- **`ConfigPanel` (侧边栏)**：允许用户动态修改坐标轴文字、象限标题、标签颜色，实时驱动前端渲染。

#### 五、 后期扩展建议 (如何实现真正的“通用”)

- **模板中心 (Template Gallery)**：在系统中内置多种模板（如“产品生命周期矩阵”、“紧急重要矩阵”），用户新建画布时，底层实际是克隆了一份对应的 JSON Schema。
- **网格化引擎**：不要把代码写死为“4个格子”。在底层设计时，画布可以被划分为`N x M` 的网格。四象限只是`2 x 2` 的特例。未来想扩展成“九宫格（3x3）商业模式画布”，只需改动 Grid 配置，渲染引擎无需重写。
- **节点自由挂载**：除了固化的四个象限，允许用户在画布上自由拖拽“便签(Sticky Notes)”到任意坐标，增加灵活性。
- **导出与分享**：基于 HTML2Canvas 或 DOM-to-Image 库，实现画布的一键截图导出，方便业务人员放入 PPT 汇报。

#### 双层版本存储模型

##### 第一层：主文档表（当前状态）

维护画布的**唯一可编辑状态**，每次保存直接更新此表，保证日常读取和协作的低延迟。[13](https://deepwiki.com/anymouschina/TapCanvas/10-project-and-workflow-management#1)

```sql
canvas_documents
  id              UUID PRIMARY KEY
  canvas_type     VARCHAR(64)      -- 'quadrant' / 'grid_9' / 'freestyle'
  title           VARCHAR(255)
  schema_version  INTEGER          -- 画布Schema的结构版本，用于迁移
  current_data    JSONB            -- 完整的画布状态（坐标轴、象限内容、节点等）
  head_revision_id UUID            -- 指向最新版本快照
  updated_at      TIMESTAMP
```

##### 第二层：版本快照表（不可变历史）

每次执行“保存版本”或自动触发时，生成一条**不可变快照**。快照本身**不重复存储完整 JSON**，而是根据与上一版本的差异情况，选择两种形态之一：

```sql
canvas_revisions
  id              UUID PRIMARY KEY
  document_id     UUID             -- 关联画布文档
  parent_id       UUID             -- 父版本，构成版本链（支持分支）
  revision_type   VARCHAR(16)      -- 'snapshot' | 'patch'
  payload         JSONB            -- snapshot: 完整JSON；patch: RFC6902 JSON Patch数组
  base_snapshot_id UUID            -- patch类型专用：所属的基础快照
  author          VARCHAR(128)
  label           VARCHAR(255)     -- 用户命名，如“v1.0 终稿”
  created_at      TIMESTAMP
```

- **Snapshot 类型**：在初始化、关键里程碑、或增量链过长时强制生成完整快照，作为**恢复锚点**。
- **Patch 类型**：日常保存生成**RFC6902 标准的 JSON Patch 数组**，只记录字段级变更（如`[{"op":"replace","path":"/quadrants/0/title","value":"探索场景v2"}]`）。`jiff` 等库可以直接完成 diff 生成与 patch 应用，一个大型画布的上百次小修改可能仅占用几 KB 存储。

#### 版本生命周期设计

##### 创建与捕获

- **手动保存版本**：用户点击“保存当前版本”，系统为`current_data` 生成快照或增量 Patch，写入`canvas_revisions`，并更新`head_revision_id`。
- **自动检查点**：按时间间隔或重大操作（如切换画布类型、批量导入）自动生成快照，防止意外丢失。
- **结构迁移绑定**：当画布的`schema_version` 升级时，自动在版本链中插入一条**迁移快照**，确保旧版本仍可被正确解析和还原。

##### 预览与恢复（原子性）

- **只读预览**：点击某个历史版本时，系统从该版本回溯到最近的基础快照，依次应用 Patch 重建完整状态，**只读加载**到画布中，不修改`current_data`，也不影响撤销/重做栈。
- **原子恢复**：确认恢复时，**不是直接覆盖**`current_data`，而是将目标历史版本重建后的状态**作为一个新的快照写入版本链的头部**，然后更新`current_data` 指向它。这样“恢复”本身也是一次可追溯的历史事件，不会破坏既有版本链。
- **一致性校验**：恢复前校验目标快照及其后代 Patch 链的完整性（如哈希比对），确保要么全部成功，要么不产生部分修改的中间状态。

##### 分支与对比

- `parent_id` 字段天然支持**版本分支**。用户可以从任一历史版本 fork 出一个新的设计分支，互不干扰地继续编辑。
- 前端提供**字段级 Diff 视图**：利用 JSON Patch 的`path` 直接定位变更位置，展示“哪个象限的哪个标题/标签被修改了”，而非笼统的文本差异。

---

#### 并发控制（多用户场景）

当多个协作者同时编辑同一画布时，版本写入需要轻量的乐观并发控制：

- 每次保存版本时附带`expected_head_revision_id`。
- 服务端在事务中校验：仅当传入的`expected_head_revision_id` 等于当前数据库中的`head_revision_id` 时，才接受写入；否则拒绝并返回最新头部，由客户端合并后重试。
- 这可以防止“过期编辑静默覆盖较新版本”。

#### 可参考的开源实现与工具

**`jiff`** （JSON Patch RFC6902 实现）可以直接用于生成画布 JSON 的 diff 和应用 patch，支持 patch 逆运算与 rebase，是双层存储模型中增量层的核心工具。

**TapCanvas**的`flows`/`flow_versions` 表设计是“当前状态表 + 不可变版本快照表”的清晰范例，其`flow_versions.data` 在每次保存时复制完整 JSON 作为不可变快照，结构简单且与你的画布场景高度同构。[13](https://deepwiki.com/anymouschina/TapCanvas/10-project-and-workflow-management#1)

**`@revisium/engine`**提供了类 Git 的分支、修订、行级 diff 与 JSON Schema 校验能力，如果未来版本管理需求变得更加复杂（如需要多分支合并、公式化迁移），可以作为后端版本引擎的参考或直接集成。[3](https://www.npmjs.com/package/@revisium/engine/v/0.6.3?activeTab=readme#1)

**buzz**的`feat(canvas): add version history` 实现中，**append-only 历史 + 原子恢复 + compare-and-swap 并发控制**的组合，可以直接借鉴到版本写入与恢复的并发安全设计中。

---

#### 与前序架构的衔接

这一版本管理方案完全建立在“画布即 JSON 文档”的前提上，因此**不需要为每一种画布类型单独设计版本表**。`canvas_type` 和`schema_version` 字段共同决定了版本数据的解析方式：四象限画布的`current_data` 和九宫格画布的`current_data` 在结构上不同，但`canvas_revisions` 的存储与恢复流程完全一致。后期新增画布类型时，只需保证其配置 JSON 可被 diff / patch，版本管理能力即自动获得。

#### 二、 前端渲染架构与层级（Z-index）

要实现图中的效果，前端渲染需要分为明确的四个图层：

- **Layer 1: 画布背景层 (Canvas Background)**
  - 负责渲染整体的斜线纹理（可以通过 CSS`repeating-linear-gradient` 实现）。
- **Layer 2: 象限网格层 (Quadrant Grid)**
  - 负责将画布切分为 4 个区域，渲染象限背景色（`backgroundColor`）。
  - 同时包含主体内容（标题、标签）和位于角落的水印（如 S/T/A/R）。
- **Layer 3: 坐标轴层 (Axes Layer)**
  - 使用 SVG 或绝对定位的 Div，悬浮在象限网格之上，渲染黑色实线轴、箭头和外围的文字标签（个人、组织、上限、下限）。**坐标轴通常需要设置为`pointer-events: none`，以免遮挡下层元素的交互**。
- **Layer 4: 自由节点层 (Markers Layer)**
  - 渲染`markers` 数组。使用`position: absolute; left: x; top: y;` 进行定位。支持配置图标、颜色和相对文字位置。

#### 三、 交互设计（自由拖拽）

图上的“人生红点”、“沙漏”等元素，在通用画布中应该允许用户拖拽调整位置。

- **拖拽实现**：在 Layer 4 中，使用类似`dnd-kit` （React）或`vuedraggable` （Vue）的库，对每个 marker 进行包裹。
- **坐标更新**：拖拽结束后，计算新的`x` 和`y` 百分比，通过事件回调更新核心 JSON 数据。
- **吸附功能 (Snapping)**：由于是象限画布，可以加入“吸附”逻辑。当节点靠近坐标轴或象限边缘时，自动吸附，保持视觉上的整齐。

#### 四、 版本管理兼容性（完美衔接）

新增的复杂元素**完全不会影响你之前设计的双轨制版本管理方案**。

- 无论是修改了背景纹理、象限水印，还是把“人生红点”从左上角拖到了中间，本质上都是对那份**JSON Schema 树的修改**。
- 系统依然会对比新旧 JSON，生成`[{ "op": "replace", "path": "/markers/0/x", "value": "50%" }]` 这样的 RFC6902 JSON Patch。
- 版本恢复时，只需依次应用 Patch，即可还原出包含特定节点位置的完整画布状态。

- **AntV Infographic**中的**“标注（Annotation）”**功能
  - **参考价值**：如何通过配置化在已有的图表上挂载散点、图标和辅助文本。
- **json-diff** (NPM 包)
  - **参考价值**：专为处理嵌套 JSON 生成的 Patch，对于包含大量 Markers 数组的复杂画布，能生成极高效的版本增量。

**架构总结**：你现在的项目本质是**“受约束的基于 DOM 的白板 + 元数据驱动渲染 + Git 风格的版本控制”**。只要把“渲染层”和“数据层”拆开，无论图片里再增加多少奇奇怪怪的图标或背景，底层架构都能稳稳兜住。
