# MetaMatrix 知识库规划文档

> **状态：第一期已实现**（目录树 + 富文本文档 + 画布挂载）。第二、三期见下文。

> 目标：在现有「项目 → 画布」结构之上，落地一套类飞书知识库能力——
> **知识目录 + 富文本文档 + 画布抽取独立 + 页面间引用**。
> 原则：复用已有 `canvas_documents` JSONB 真源与抽取层，不推倒重建。

---

## 一、现状盘点（复用基础）

| 已有能力 | 落点 | 知识库如何复用 |
| --- | --- | --- |
| 画布文档 JSONB 真源 | `canvas_documents.current_data` | 文档正文也走同一张表，新增 `canvasType = "doc"` |
| 内容抽取层 | `canvas_content_blocks` + `content_text` + `content_tsv` | 文档检索直接复用，无需新表 |
| 修订历史 | `canvas_revisions`（snapshot/patch） | 文档版本历史天然继承 |
| 富文本编辑器 | `components/RichTextEditor.vue` + `components/rte/*` | 文档正文编辑器直接复用 |
| 画布引用节点 | `nodeGraph/` 的 CanvasRefNode | 页面引用画布已有原型 |
| 项目容器 | `projects` 表 + `ProjectListView` | 知识空间 = 项目；目录树挂在项目下 |
| 搜索 | `GET /documents/search` | 全文检索已支持，加目录过滤即可 |
| 乐观锁 | `save_version` CAS | 文档并发保存天然支持 |
| 媒体上传 | `media/` handler + chunked upload | 文档内图片/附件复用 |

**结论：不新建文档表，不新建编辑器，不新建搜索。** 只补「目录树」和「引用语义」两层。

---

## 二、目标架构

```
知识空间 (Project)
├── 目录树 (KnowledgeTree)          ← 新增
│   ├── 文件夹节点
│   └── 文档叶子节点
│       ├── 富文本文档 (canvasType=doc)   ← 复用 RichTextEditor
│       └── 画布文档 (现有 80 种模板)     ← 抽取为独立页面类型
└── 页面引用 (PageReference)        ← 新增
    ├── 文档 → 画布 引用
    ├── 文档 → 文档 引用
    └── 画布 → 画布 引用（已有 nodeGraph）
```

## 三、四块能力拆解

### 1. 知识目录

**问题**：现在画布只有扁平列表（`GET /documents?templateId=`），没有树。

**方案**：新增 `knowledge_nodes` 表，目录树与文档解耦——节点只存父子关系和排序，文档本身仍在 `canvas_documents`。

```sql
knowledge_nodes
  id            uuid PK
  project_id    uuid NOT NULL INDEX      -- 所属知识空间
  parent_id     uuid NULL INDEX          -- NULL = 根级
  node_type     varchar(16)              -- 'folder' | 'doc'
  document_id   uuid NULL                -- doc 节点指向 canvas_documents.id；folder 为 NULL
  title         varchar(255) NOT NULL    -- 节点显示名
  sort_order    int DEFAULT 0
  icon          varchar(16)              -- emoji，默认 📄/📁
  created_at    timestamptz
  updated_at    timestamptz
  UNIQUE(project_id, parent_id, title)   -- 同级不重名
  INDEX(project_id, parent_id, sort_order)
```

- 目录树操作：移动、拖拽排序、重命名、删除（删文件夹级联删子节点，文档本身软删）
- `document_id` 外键 `ON DELETE SET NULL`——文档被删后节点保留为「已失效」占位，与现有 nodeGraph 引用语义一致
- 树查询：单条 SQL `WHERE project_id = ? ORDER BY parent_id NULLS FIRST, sort_order` 前端一次拉全量构建，不递归查询

**API**：
```
GET    /projects/:projectId/knowledge/tree        -- 整棵树
POST   /projects/:projectId/knowledge/nodes        -- 新建节点（folder/doc）
PATCH  /projects/:projectId/knowledge/nodes/:id    -- 重命名 / 移动 / 排序
DELETE /projects/:projectId/knowledge/nodes/:id    -- 删节点（级联子节点）
```

**前端**：`KnowledgeTree.vue`——Element Plus `el-tree` + 拖拽，复用 `ProjectDetailView.vue` 的布局壳。

### 2. 富文本文档

**问题**：用户要的是「知识库文档」，不是「画布文档」。

**方案**：新增 `canvasType = "doc"`，`current_data` 存 TipTap JSON（`{ type: "doc", content: [...] }`），直接喂给现有 `RichTextEditor.vue`。

- 模板注册：`stores/document.ts` 的 `TEMPLATE_META` 加 `doc` 条目
- 路由：`/projects/:projectId/doc/:documentId`（与 `/canvas/:templateId` 平级）
- 编辑器：复用 `RichTextEditor` 的 `compact` + `page-sheet` 模式，已有页面设置面板（页眉页脚、页边距、水印）直接可用
- 文档模板：复用 `rteDocTemplates.ts`（周报 / 会议纪要 / 需求文档等），新建时选择模板插入
- 保存：走现有 `PUT /documents/:id`，乐观锁 `saveVersion` 不变

**抽取层适配**：`content.TextLines` walker 对 `doc` 类型的 TipTap JSON 天然有效（已有 `text`/`content` 键递归），无需改 walker。

---

### 3. 画布抽取独立

**问题**：现在画布是「模板驱动的一整页」，和文档混在一起，用户想要「画布作为独立页面类型挂在目录树里」。

**方案**：画布已经是独立文档（`canvas_documents` 一行 = 一张画布），只需让目录树能挂画布节点。

- `knowledge_nodes.node_type = 'doc'` 时 `document_id` 指向任意 `canvasType` 的文档（包括 `doc` 和 80 种画布模板）
- 打开画布节点：路由按 `canvasType` 分流——`doc` → `DocView`，其余 → `HomeView`（现有画布渲染器）
- 画布列表页（`ProjectDetailView.vue`）仍保留，作为「未归类画布」入口；目录树是另一套组织维度，两套共存

**不改画布渲染器本身**，只改入口路由和目录挂载。

---

### 4. 页面文档引用

**问题**：飞书有「@文档」和「嵌入画布」，现在只有 nodeGraph 里的画布引用节点。

**方案**：两层引用——

**(a) 文档内 @ 引用（富文本 mention 扩展）**

现有 `rteMentionItems.ts` 已有 @ 人的目录。扩展为 @ 文档：

- 数据源：`GET /projects/:projectId/knowledge/tree`（或 `GET /documents/search?q=`）
- 渲染：mention 节点带 `documentId` + `title`，点击跳转 `/projects/:projectId/doc/:documentId`
- 存储在 TipTap JSON 的 `mention` 节点 attrs 里，不单独建引用表

**(b) 文档嵌入画布（block embed）**

现有 `rteEmbeddedPaper.test.ts` 已有嵌入画布原型。正式化：

- TipTap 扩展 `rteCanvasEmbed`：插入一个「画布引用块」，attrs 存 `canvasDocumentId`
- 渲染：块内 iframe 或内联渲染目标画布的只读快照
- 只读：嵌入的是快照引用，源画布更新后嵌入处可手动刷新（不自动同步，避免性能问题）

**(c) 反向引用索引（可选，第二阶段）**

如果要做「这篇文档被哪些文档引用了」的反查：

```sql
page_references
  id           uuid PK
  project_id   uuid NOT NULL INDEX
  source_doc   uuid NOT NULL    -- 引用方文档
  target_doc   uuid NOT NULL    -- 被引用文档
  anchor       varchar(64)      -- mention 节点 id / embed 块 id
  created_at   timestamptz
  UNIQUE(source_doc, target_doc, anchor)
```

保存文档时从 TipTap JSON 里扫 mention/embed 节点，重写这张表。第一阶段可不做，@ 和 embed 本身不带反查。

## 四、实施分期

### 第一期：目录树 + 富文本文档（核心闭环）

## 五、关键约束（踩坑预警）

- **目录树不存文档内容**：`knowledge_nodes` 只存结构，文档正文仍在 `canvas_documents.current_data`。目录树删除不删文档，文档删除不删目录树（留失效占位），与现有 nodeGraph 语义一致。
- **canvasType 不新增业务表**：`doc` 类型和 80 种画布模板一样走 JSONB，不建 `documents` 表。遵循 `GLOBAL_RULES/content-retrieval-ai.md`。
- **拖拽排序用 sort_order 整数**：不用 ltree / 物化路径，同级排序用整数足够，跨级移动改 parent_id。树深度一般 ≤ 3 层。
- **@ mention 不建引用表**：mention 是文档内联引用，存在 TipTap JSON 里，不需要独立关系表。只有需要反查时才建 `page_references`。
- **画布嵌入只读**：嵌入的画布是快照引用，不在嵌入处编辑，避免双编辑器抢焦点和并发保存问题。
- **搜索复用**：`content_text` + `content_tsv` + `canvas_content_blocks` 对 doc 类型天然有效，不加新索引。

## 七、数据流

```
用户在目录树新建「需求文档」
  → POST /knowledge/nodes (nodeType=doc, title=需求文档)
    → 后端建 knowledge_nodes 行 + 建 canvas_documents 行 (canvasType=doc, currentData={type:doc,content:[]})
      → 返回 node + documentId
        → 前端路由到 /doc/:documentId
          → RichTextEditor 加载 currentData
            → 编辑 → PUT /documents/:id (saveVersion CAS)
              → 保存时 walker 抽 content_text + content_blocks
                → 搜索可命中
```

**逆向：搜索命中文档**
```
GET /documents/search?q=需求
  → content_tsv 命中 → 返回 SearchHit (含 panelId)
    → 点击 → 找到所属 knowledge_node → 路由跳转 → 打开文档
```
